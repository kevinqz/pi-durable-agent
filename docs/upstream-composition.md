# Upstream composition and reduction review

[Roadmap](./roadmap.md) · [Architecture](./architecture.md) · [OptChat plan](https://github.com/kevinqz/optchat-durable/blob/main/docs/development/upstream-composition.md)

Reviewed against the operational 0.1.0 source, Pi 1.1.0, Agents 0.28.0, Code Mode 0.5.3 and OptChat 0.4.0. The integration uses upstream runtimes; it is not the origin of durable agents, tool approvals or conversation compaction. The objective of this track is to remove duplicate ownership while retaining supported recovery and existing data.

## Decisions by boundary

| Candidate                                 | Decision                                            | Evidence and constraint                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pi loop, transcript and tool recovery     | Reuse upstream                                      | `AgentSession` constructs the official `PiHarness` and `Harness`; OptChat submits to Pi. There is no replacement model loop.                                                                                                                                                                                                                                                                               |
| Request status projection                 | Consolidate in OptChat, consume in this application | Both repositories interpreted the same native task fault. OptChat 0.4.1 makes `request(id)` agree with `status().requests`. The app maps only the public `done` label to its existing `completed` label. Polling reuses the returned status records instead of fetching each document and task again.                                                                                                      |
| Application request ledger                | Retain the admission/policy ledger                  | It holds body-conflict checks, HTTP acceptance before SDK admission, user backlog quotas, reserved result-delivery slots and timestamps. OptChat's queue is memory preparation; Pi's inbox is model execution. They are different commit boundaries. Deleting the application ledger would lose a tested pre-admission recovery window.                                                                    |
| Normal request wakes                      | Retain the documented adapter                       | `PiHarness.submit()` creates native session wakes, but it bypasses OptChat's preparation controller. Public `PiHarness.pi()` exposes the harness without a public arbitrary-task admission/wake callback. Host jobs reserve a wake before `chat.enqueue()` and survive a crash before it. No private `PiHarness.enqueue` or job identifier is used.                                                        |
| Facet job bridge                          | Retain, with explicit replacement criteria          | `FacetLifecycle` stores child job intentions in the subtree that native clone copies. The root owns official Lifecycle alarms, leases and reset protection. Agents already routes Scheduler capability jobs to a root, but those root-owned jobs do not participate in the child checkpoint. Generic routing is not a demonstrated drop-in replacement for this Pi/application task and snapshot contract. |
| Checkpoint coordinator                    | Retain the application protocol over native clone   | The platform owns `ctx.facets.clone/abort/get`. The app must freeze admission, compare the copied state, activate a generation and exclude destination effects and budget counters from rewind. Pi compaction, forks and restart recovery do not establish that combined contract.                                                                                                                         |
| Code Mode script replay and pending calls | Reuse upstream                                      | Call `execute`, `approve`, `reject`, `executions` and `pending`; Code Mode owns its replay log. The application does not replay connector call logs itself.                                                                                                                                                                                                                                                |
| Action record and final delivery          | Retain the application outbox/policy                | Code Mode execution identity is allocated by `execute`; it does not accept our stable admission ID. Persisting the dispatch boundary prevents an uncertain call from creating a second execution. The app additionally owns owner/expiry/generation checks, approval fingerprint and a separately acknowledged result delivered to Pi.                                                                     |
| Retained executor output                  | Retain the bounded application archive              | The app preserves its supported output before the model-facing projection and serves it through its authenticated export/UI contract. It does not duplicate every Code Mode table or advertise a portable execution backup.                                                                                                                                                                                |
| Browser transport and user interface      | Keep as application presentation                    | PiHarness deliberately leaves HTTP/WebSocket/RPC transport to the host. Moving to Think's ready-made protocol would change the harness and memory strategy; it is not a transparent package substitution.                                                                                                                                                                                                  |
| Provider input shaping                    | Keep the narrow documented callback                 | The GPT-OSS text-parts normalization uses Pi's public `onPayload`. No dependency is patched. Remove it only when a qualified provider release handles the same input natively.                                                                                                                                                                                                                             |

## Attack sequence and acceptance

1. **OptChat owns the generic correction.** Publish 0.4.1 with one read-only request projection. Preserve every stored task/document identity and the native Pi extension behavior.
2. **Agent removes duplicated interpretation.** Pin that exact artifact. Consume its public status in individual refresh and list snapshots; retain HTTP/API labels and policy records. A native task fault and object reset must remain visible without inference or replay.
3. **Qualify the exact update.** Run 0.1.0 with its own installed dependencies and the new application with its own lockfile. Copy state into a separate destination; verify legacy and checkpoint sessions, history, memory, pending approvals, completed effects and delivery. Retain but reject old-build checkpoints and create a new compatible checkpoint. A symlink to the new dependency tree is only acceptable when the entire dependency graph is identical.
4. **Publish independent evidence and upgrade route.** Do not change old tags, discard checkpoints or claim that an old checkpoint works under a new backend. A local full-state update and a same-build hosted checkpoint restore are different operations.
5. **Keep upstream replacement triggers explicit.** Revisit the bridge if PiHarness gains a public wake contract for host-admitted tasks or Lifecycle supports equivalent snapshot-owned child intentions. Revisit the outbox if Code Mode provides stable execute-or-attach admission and durable acknowledgement by the consuming harness. A new API must pass the existing failure-window fixtures before replacing these boundaries.

The decision for the other overlap candidates is **retain with a specific contract**, not an assertion that the current architecture is globally minimal. No new scheduler, orchestration framework, connector or performance study is introduced by this reduction.

## Two independent repositories

OptChat is usable without this application. Generic memory and controller defects are fixed and released there first. This repository pins its published artifact, never a source checkout or moving branch. Cloudflare configuration, ownership, action policy, session recovery and transport stay here. Each project links to the other's canonical plan instead of copying a second live delivery log.

## Alternatives and evidence limits

Cloudflare Think already provides a complete harness with memory, compaction, search, durable submissions and recovery. It is a reasonable alternative for a generic hosted assistant. Choosing it here would require a distinct comparison of memory semantics and a reviewed migration, not running a second harness alongside Pi merely to reuse a transport. Current functional checks do not establish that OptChat is better than native Pi or Think in recall, cache efficiency, cost or latency.
